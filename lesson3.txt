מה זה CRUD?
בפיתוח צד-שרת (Backend), השם CRUD הוא ראשי תיבות של ארבע הפעולות הבסיסיות ביותר שניתן לבצע על מידע המאוחסן במסד נתונים (Database):

C - Create (יצירה): הוספת נתון חדש למערכת.

R - Read (קריאה / שליפה): הצגה או קבלה של נתונים קיימים.

U - Update (עדכון): שינוי או עדכון של נתונים קיימים.

D - Delete (מחיקה): הסרת נתון מהמערכת.

כמעט כל תוכנה או מערכת שאת פוגשת ביומיום מסתמכת על ארבע הפעולות האלו כדי לנהל את המידע שלה.

למה כמעט כל אפליקציית Backend צריכה פעולות CRUD?
רוב האפליקציות אינן סטטיות – תפקידן העיקרי הוא לנהל מידע שמשתנה לאורך זמן. ללא פעולות CRUD, לאפליקציה לא הייתה דרך לשמור על עקביות הנתונים או לאפשר למשתמשים ליצור אינטראקציה אמיתית עם המערכת:

ניהול מחזור החיים של מידע: מידע נוצר, משתנה ולבסוף עשוי להימחק. CRUD מספק את המסגרת המלאה לניהול הנתונים מתחילת דרכם ועד סופם.

תקשורת אחידה: CRUD מגדיר תקן ברור ומקובל בין צד-הלקוח (Client) לבין צד-השרת (Backend), מה שמפשט את התכנון והפיתוח של המערכת.

התאמה לפרוטוקול אינטרנט (HTTP): בעולם ה-Web, פעולות CRUD מתורגמות באופן טבעי לבקשות HTTP מוכרות (כמו POST ליצירה, GET לקריאה, PUT/PATCH לעדכון, ו-DELETE למחיקה).

1. Create (יצירה)
תרחיש: מנהל המערכת פותח קורס חדש לשנת הלימודים.

מה קורה ברקע: צד-השרת מקבל את פרטי הקורס (שם הקורס, שם המרצה, מספר שעות) ויוצר רשומה חדשה במסד הנתונים.

2. Read (קריאה / שליפה)
תרחיש: תלמידה נכנסת למערכת כדי לראות את רשימת הקורסים הזמינים או לצפות בפרטי קורס ספציפי.

מה קורה ברקע: צד-השרת שולף את פרטי הקורס מתוך מסד הנתונים ומציג אותם על המסך.

3. Update (עדכון)
תרחיש: מועד סיום הקורס השתנה, או שהוחלט להחליף את כיתת הלימוד.

מה קורה ברקע: המשתמש מזין את הנתונים המעודכנים, וצד-השרת מעדכן את הרישום הקיים של אותו קורס במסד הנתונים.

4. Delete (מחיקה)
תרחיש: קורס בוטל מחוסר הרשמה ואין בו צורך יותר במערכת.

מה קורה ברקע: צד-השרת מוצא את הקורס המבוקש ומסיר אותו באופן קבוע (או מסמן אותו כמבוטל) במסד הנתונים.

בפיתוח צד-שרת (Backend) ובתקשורת באינטרנט, הפעולות הבסיסיות של CRUD מבוצעות בדרך כלל באמצעות שיטות (Methods) של פרוטוקול HTTP. שיטות אלו הגדירות לשרת איזו פעולה אנו מבקשים לבצע על הנתונים.

הנה הסבר על כל שיטה והדגמה מעשית עבורה:

1. GET (קריאה / שליפה)
מה היא עושה: מבקשת לקבל או לקרוא נתונים קיימים מהשרת. בקשת GET אינה אמורה לשנות, להוסיף או למחוק מידע בשרת – היא נועדה רק לצפייה.

דוגמה מעשית: משתמש נכנס לדף פרופיל המשתמש שלו באתר. הדפדפן שולח בקשת GET לשרת כדי לקבל את פרטי המשתמש (שם, כתובת אימייל, תמונת פרופיל) ולהציג אותם על המסך.

2. POST (יצירה / הוספה)
מה היא עושה: שולחת נתונים חדשים לשרת כדי ליצור משאב חדש במסד הנתונים.

דוגמה מעשית: משתמש ממלא טופס הרשמה לאתר עם שם משתמש, סיסמה וכתובת אימייל, ולוחץ על "הרשמה". הדפדפן שולח בקשת POST עם הנתונים הללו, והשרת יוצר משתמש חדש במערכת.

3. PUT (עדכון מלא)
מה היא עושה: שולחת מידע מעודכן לשרת כדי להחליף או לעדכן משאב קיים. בדרך כלל, בקשת PUT מעבירה את אובייקט הנתונים המלא עם השינויים.

דוגמה מעשית: משתמש נכנס לדף הגדרות החשבון שלו, משנה את שם המשפחה ואת מספר הטלפון שלו, ולוחץ על "שמירת שינויים". הדפדפן שולח בקשת PUT לשרת עם הפרטים המעודכנים, והשרת מעדכן את הרשומה של אותו משתמש במסד הנתונים.

4. DELETE (מחיקה)
מה היא עושה: מבקשת מהשרת להסיר או למחוק משאב מסוים הקיים במסד הנתונים.

דוגמה מעשית: משתמש לוחץ על כפתור "מחק משימה" ברשימת המשימות שלו. הדפדפן שולח בקשת DELETE עם מזהה המשימה הספציפית, והשרת מסיר אותה ממסד הנתונים.

מה זה REST API?
כדי להבין מה זה REST API, נעזר באנלוגיה פשוטה:

דמייני שאת יושבת במסעדה.

את (הלקוח / Client): רוצה להזמין אוכל.

המטבח (השרת / Backend): מכין את המזון ומחזיק את כל המצרכים.

המלצר (ה-API): מעביר את ההזמנה שלך למטבח ומחזיר אלייך את המנה המוכנה.

API (ראשי תיבות של Application Programming Interface) הוא פשוט "המלצר" שמקשר בין האפליקציה בטלפון או בדפדפן לבין השרת שבו שמור המידע.

REST היא סדרה של עקרונות וכללים שקובעים איך המלצר הזה אמור לעבוד בצורה מובנית, פשוטה ויעילה.

למה משתמשים בשיטות HTTP במקום בשמות של פעולות בכתובת (URL)?
כשמעצבים REST API, הכתובת (URL) מייצגת משאב (Resource) – כלומר את ה"דבר" שאנחנו עובדים איתו ( כמו משתמשים, מוצרים או הודעות), ולא את הפעולה שאנחנו עושים עליו.

הגישה הישנה (ללא REST):
בעבר, לכל פעולה היו יוצרים כתובת URL נפרדת שהכילה את שם הפעולה:

[https://example.com/getUser](https://example.com/getUser) (לקבלת משתמש)

[https://example.com/createUser](https://example.com/createUser) (ליצירת משתמש)

[https://example.com/updateUser](https://example.com/updateUser) (לעדכון משתמש)

[https://example.com/deleteUser](https://example.com/deleteUser) (למחיקת משתמש)

הבעיה: השיטה הזו יוצרת ריבוי עצום של כתובות שונות, מבולבלות וקשות למעקב.

הגישה של REST API:
ב-REST API, הכתובת נשארת קבועה ומייצגת רק את המשאב, ואת הפעולה שרוצים לבצע מגדירים באמצעות שיטת ה-HTTP (כמו GET, POST, PUT, DELETE).

לדוגמה, עבור משאב של משתמשים (/users):

שיטת HTTP	כתובת URL	מה הפעולה עושה?
GET	/users	מביאה את רשימת המשתמשים
POST	/users	יוצרת משתמש חדש
PUT	/users/123	מעדכנת את משתמש מספר 123
DELETE	/users/123	מוחקת את משתמש מספר 123
היתרונות של שימוש בשיטות HTTP:
איחוד ופשטות (Standardization): הכתובות קצרות, ברורות ונקיות. אין צורך להמציא שמות שונים לפעולות לכל שרת.

הפרדה ברורה: הכתובת (URL) מתארת מה המשאב, ושיטת ה-HTTP מתארת מה עושים איתו.

התנהגות צפויה: כל מפתח שמכיר את תקן REST מבין מיד מה כל נתיב עושה, מבלי לעיין בתיעוד מורכב.

תכנון נכון של REST API מתבסס על כמה עקרונות ליבה שמבטיחים שהמערכת תהיה נוחה לשימוש, ברורה למפתחים, ויציבה לאורך זמן.

הנה העקרונות המרכזיים שחשוב להכיר:

1. שמות עצם ברבים (Nouns in Plural)
שמות הנתיבים (Endpoints) צריכים לייצג משאבים (Resources) ולא פעולות, ולהיות בלשון רבים.

נכון: GET /api/books, POST /api/authors

לא נכון: GET /api/getBook, POST /api/createNewAuthor

2. היררכיה ויחסים בין משאבים
כאשר משאב אחד שייך למשאב אחר, מייצגים זאת במבנה הכתובת בצורה היררכית:

GET /api/authors/5/books – שליפת כל הספרים ששייכים למחבר שמזההו הוא 5.

POST /api/authors/5/books – יצירת ספר חדש המשויך למחבר מספר 5.

3. שימוש נכון בקוד סטטוס של HTTP (Status Codes)
השרת צריך להחזיר תגובה עם קוד סטטוס מתאים שמסביר מה קרה בבקשה:

200 OK: הבקשה הצליחה (למשל ב-GET או PUT).

201 Created: משאב חדש נוצר בהצלחה (בבקשת POST).

400 Bad Request: הבקשה של הלקוח לא תקינה (למשל נתונים חסרים בטופס).

401 Unauthorized / 403 Forbidden: בעיית הרשאות או גישה.

404 Not Found: המשאב המבוקש לא נמצא.

500 Internal Server Error: שגיאה פנימית בשרת.

עימוד (Pagination): GET /api/books?page=2&limit=20

סינון (Filtering): GET /api/books?category=science

מיון (Sorting): GET /api/books?sort=title

ב-Express, שתי הדרכים הנפוצות לקבל מידע המגיע מהלקוח לשרת הן דרך req.params ודרך req.body.

1. req.params (פרמטרים בנתיב ה-URL)
req.params מכיל משתנים המוגדרים כחלק מנתיב ה-URL עצמו (Path Parameters). הם מוגדרים בנתיב השרת בעזרת נקודתיים (:).

מתי משתמשים ב-req.params?
כאשר הנתון מזהה באופן ספציפי משאב בודד במערכת (כמו מזהה ייחודי / ID).

מיועד בעיקר לבקשות מבוססות מזהה כגון שליפת פריט מסוים (GET), עדכון פריט מסוים (PUT/PATCH), או מחיקת פריט מסוים (DELETE).

דוגמה לשימוש:
כתובת הבקשה: GET /api/books/102

הגדרת הנתיב בשרת: /api/books/:id

הערך ב-req.params: { id: "102" }

2. req.body (גוף הבקשה / Payload)
req.body מכיל נתונים שנשלחים בתוך גוף הבקשה (שאינם מוצגים בכתובת ה-URL עצמה). ברוב המקרים, הנתונים נשלחים במבנה אובייקט JSON.

(כדי להשתמש ב-req.body ב-Express, נדרש להשתמש במידול מובנה המפענח JSON).

מתי משתמשים ב-req.body?
כאשר מעבירים כמות גדולה או מורכבת של נתונים (כמו טפסים, אובייקטים מרובי שדות וכדומה).

כאשר הנתונים מכילים מידע שאיננו רוצים להציג גלוי בכתובת ה-URL.

מיועד בעיקר לבקשות יצירה (POST) או עדכון נתונים (PUT/PATCH).

דוגמה לשימוש:
בקשת POST לכתובת: /api/books

הנתונים שנשלחים בגוף הבקשה (Body):

JSON
{
  "title": "Clean Code",
  "author": "Robert C. Martin",

הערך ב-req.body: האובייקט המלא שנשלח, נגיש בשרת דרך req.body.title, req.body.author וכו'.

בשרת Express, חילוץ מידע שמגיע מבקשות הלקוח הוא חלק מרכזי בטיפול בבקשות (Request Handling). מעבר ל-req.params ו-req.body, ישנם מספר מנגנונים נוספים ואמצעים חשובים שבאמצעותם השרת מחלץ ומעבד נתונים:

1. חילוץ כותרות (Headers) – req.headers
כותרות ה-HTTP מכילות מידע מטא-נתונים (Metadata) על הבקשה עצמה, כגון סוג התוכן, פרטי הזדהות, או אסימוני אבטחה (Tokens).

למה זה משמש: אימות משתמשים (Authentication), זיהוי סוג הלקוח (User-Agent), או הגדרת פורמט הנתונים.

איך ניגשים לזה:

ניתן לקבל את כל האובייקט דרך req.headers.

ניתן לשלוף כותרת ספציפית בעזרת req.get('header-name').

2. מנגנוני תיווך לחילוץ גוף הבקשה (Body Parsers)
כדי ש-Express יוכל לקרוא ולחלץ נתונים מתוך req.body, הוא חייב להשתמש ב-Middleware (פונקציות תיווך) הממירות את פעימות המידע הגולמיות (Raw Data Buffers) שמגיעות ברשת לאובייקטים נגישים.

בגרסאות העדכניות של Express, מנגנונים אלו מובנים בפריים-וורק:

express.json(): מיועד לחילוץ נתונים שנשלחו בפורמט JSON.

express.urlencoded({ extended: true }): מיועד לחילוץ נתונים שנשלחו מתוך טפסי HTML סטנדרטיים (form submit).

3. חילוץ קבצים (File Uploads)
כאשר הלקוח מעלה קובץ (כמו תמונה או מסמך), המידע אינו נשלח כ-JSON רגיל אלא במבנה שנקרא multipart/form-data. Express אינו יודע לחלץ קבצים אלו באופן מובנה, ולכן משתמשים בספריות תיווך ייעודיות (כמו multer).

איך המידע נגיש לאחר החילוץ:

הקובץ המועלה מחולץ אל req.file (לקובץ יחיד) או req.files (למספר קבצים).

שדות המלל הרגילים שנשלחו לצד הקובץ עדיין יופיעו ב-req.body.

4. חילוץ מידע מותאם אישית דרך Middleware
פעמים רבות תרצה לחלץ מידע, לפרק אותו, ואז להצמיד אותו ל-req כדי שיהיה זמין בהמשך הטיפול בבקשה.

דוגמה נפוצה (אימות משתמש):

פונקציית תיווך מבודדת את אסימון הגישה (Token) מתוך req.headers.

הפונקציה מפענחת את האסימון ומחלצת ממנו את פרטי המשתמש (למשל userId).

הפרטים המחולצים מוצמדים למשתנה חדש, למשל: req.user = decodedUser.

הפונקציה הבאה בשרת יכולה לגשת ישירות ל-req.user.
